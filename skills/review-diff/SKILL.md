# 代码审查技能 (review-diff)

当用户要求「审查代码」「看看这次改动有没有问题」「review 一下 diff」时，
按以下流程执行。

## 审查流程

1. 用 `read` 读取被修改文件的当前内容，建立整体认知
2. 若用户粘贴了 diff，逐块（hunk）阅读；若没有 diff，
   询问用户改动范围，或用 `bash` 执行 `git diff` 获取
3. 对照下面的清单逐项检查
4. 按输出格式给出结论

## 检查清单

- **危险操作**：删除目录、`rm -rf`、格式化磁盘、强制覆盖未备份文件
- **安全**：硬编码密钥/密码、绕过 `.env` 等安全拦截、把用户输入直接拼进命令
- **错误处理**：裸 `except:` 吞掉异常、失败路径返回了成功状态码
- **资源**：文件/网络连接是否用 `with` 或显式关闭
- **边界**：空输入、超长输入、并发访问、路径含空格或中文
- **行为变化**：这次改动会不会破坏既有调用方（改了函数签名、改了返回结构）

## 输出格式

```
### 结论
（通过 / 有风险 / 必须修改）

### 问题列表
| 严重度 | 位置 | 问题 | 建议 |
|:---|:---|:---|:---|

### 亮点
（做得好的地方，1-2 条，没有可省略）
```

## 纪律

- 每个问题都要引用行号或原文片段，不许空泛指控
- 严重度分三级：**必须修改**（会出错/出事故）、**有风险**（特定条件触发）、**建议**（更优写法）
- 不要为了凑数报告纯风格类小问题
